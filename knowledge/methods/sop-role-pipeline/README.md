# SOP Role Pipeline

## 什么时候使用

| 判断 | 内容 |
| --- | --- |
| 要解决的问题 | 多 agent 自由对话缺少结构约束：任务分解边界不清、中间产物散失在聊天记录中、单个角色的错误沿对话链传播。 |
| 使用前提 | 任务流程可预先编码为阶段性角色序列（SOP）；每个角色能产出结构化中间产物；允许为角色定义系统提示与消息订阅规则。 |
| 输入 | 角色配置（名称、职责、产出类型、订阅的消息类型）、SOP 顺序、任务描述与模型回调。 |
| 输出 | 按角色顺序产出的结构化产物链与消息池记录；评审打回时附带修复轮次记录。 |
| 不使用 | 任务流程无法预先定义（探索型任务）；单角色足以完成；角色拆分带来的重复读取会使 token 成本超过收益。 |
| 主要风险 | SOP 僵化，任务与预设流程不匹配时效率下降；上游角色的错误沿流水线传播，只能靠评审角色拦截；角色数增长使 token 与墙钟成本线性上升。 |

## 怎么工作

1. 把任务流程编码为角色序列（如 分析 → 实现 → 评审），每个角色有固定职责与结构化输出格式。
2. 角色产出结构化中间产物（而非自由聊天文本），作为下游角色的输入契约。
3. 消息经发布-订阅池分发：角色只接收自己订阅类型的消息，减少无关上下文；同一生产者只保留最新产物。
4. 评审角色对产物给出 PASS / REVISE 判定；REVISE 时按反馈打回上游重产（有限轮次），通过后继续。
5. 全部产物与消息记录可导出，供诊断与复用。

本方法改造的是 harness 的编排层与多 agent 协作模块，不修改执行模型与工具层。与 [Nested Subagent Delegation](../nested-subagent-delegation/README.md)（动态选择发言者、递归委派）互补：SOP 流水线是固定顺序的静态编排，适合流程已知的任务；两者可组合（流水线角色内部再嵌套子会话）。

方法关系：与 Nested Subagent Delegation 是组合关系；结构化产物与消息记录可作为 [Action-Observation Event Stream](../action-observation-event-stream/README.md) 的记录单元。与自由群聊式多 agent 是替代关系。以上均为待实验验证的假设，尚无本地证据。

## 直接运行

```bash
python code/sop_pipeline.py demo
```

| 文件 | 用途 |
| --- | --- |
| [`code/sop_pipeline.py`](code/sop_pipeline.py) | 角色定义、发布-订阅消息池、SOP 流水线与评审打回的机制骨架；模型调用以回调注入。 |
| [`code/sop_prompt.md`](code/sop_prompt.md) | 角色执行与评审判定的提示模板。 |
| [`code/requirements.txt`](code/requirements.txt) | Python 依赖清单；当前实现仅使用标准库。 |
