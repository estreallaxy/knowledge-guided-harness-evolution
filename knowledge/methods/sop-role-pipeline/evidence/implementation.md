# 实现依据

核对代码来源：[`geekan/MetaGPT`](https://github.com/geekan/MetaGPT)（论文对应 ICLR 2024 版实现）。关键位置按上游模块粒度标注，精确文件路径待对照固定版本复核。

| 环节 | 论文/上游行为 | 关键位置 |
| --- | --- | --- |
| 角色与 SOP | 产品经理 → 架构师 → 项目经理 → 工程师 → QA 的角色流水线，每角色有固定职责与提示 | `metagpt/roles/`（各角色类） |
| 结构化产物 | 角色产出 PRD、设计文档、接口定义等结构化中间产物，而非自由聊天 | `metagpt/actions/`（产出动作，如写 PRD / 写代码） |
| 发布-订阅消息 | 角色按消息类型订阅，环境按类型分发消息 | `metagpt/schema.py`（Message）与环境模块 |
| 执行反馈循环 | QA 运行生成的代码并按报错迭代修复 | 代码执行与调试动作 |

## 输入输出约定

```text
角色配置（名称 + 职责 + 产出类型 + 订阅类型）+ 任务 + 模型回调
                    ↓
   按 SOP 顺序逐角色执行（读取订阅消息，产出结构化产物）
                    ↓
   评审角色判定 PASS / REVISE；REVISE 打回上游重产（有限轮）
                    ↓
   结构化产物链 + 消息池记录
```

## 本仓库代码

[`../code/sop_pipeline.py`](../code/sop_pipeline.py) 按上述机制重新实现为与 harness 无关的骨架，而非复制上游代码。差异：角色、订阅类型与评审关系全部配置化，不内置任何具体业务角色；产物为纯文本结构化输出，不包含上游的文档解析与代码执行组件；模型调用以回调注入。迁移到 Terminus-KIRA 时，可先用「分析 → 修改 → 评审」三角色流程验证机制触发与成本，再按需增加角色。

上游仓库当前未复制进仓库；其运行依赖和可复现性仍需通过实际复现确认。
