A.1. Optimization Cost
We provide a detailed cost comparison of self-supervised methods on GSM8K in Table 4. All optimizations follow the
authors’ default settings, with inputs adapted to match our method (one data sample without answers). The comparison
includes the number of API calls, input tokens, output tokens, estimated price cost, and optimization time. All methods
utilize GPT-4.1-nano as the base LLM, and the price cost is estimated based on Azure OpenAI’s pricing ($0.10 per 1M input
tokens and $0.40 per 1M output tokens). Our method strikes a good balance between cost and performance, incurring only
slightly higher costs than SPO while delivering significantly better performance. We draw Figure 4 in the main paper based
on this table.

                                Table 4. Cost comparison of self-supervised methods on GSM8K.

                 Method             Number of         Input          Output       Price Cost        Time
                                    API Calls        Tokens          Tokens        ($USD)         (minutes)
                 GLaPE                 1660          322,747         198,385        0.112           ∼90

                 PromptWizard           154          39,385          46,671         0.023           ∼12
                 MR.PEA (Ours)          57           48,519          12,173         0.010           ∼2



To further clarify MR.PEA’s overhead, we break down the approximate token usage for each phase of the pipeline on
GSM8K. In the results above, MR.PEA updated the knowledge only once. If knowledge is updated at every iteration, the
total token and time cost increases moderately, as shown in Table 5.

                                    Table 5. Token usage per phase in MR.PEA on GSM8K.

                 Phase                                Input Tokens                 Output Tokens
                 Phase 1 – Knowledge curation            ∼1000           ∼250 (if update); ∼25 (if no update)
                 Phase 2 – Example generation            ∼1500                          ∼250
                 Phase 3 – Prompt refinement             ∼1300                          ∼150
                 Phase 4 – Evaluation execution         ∼180×2                        ∼330×2
                 Phase 4 – Evaluation comparison         ∼1600                          ∼130
                 Total (update once)                    ∼54,600                       ∼12,300
                 Total (update every time)              ∼57,600                       ∼14,400


In practice, updating knowledge once typically takes 2–2.5 minutes, while updating at every iteration would require 3 more
calls and 2.5–3 minutes in total. This is because our implementation includes a mechanism to skip unnecessary updates: if
the knowledge has already been sufficiently reflected in recent iterations (i.e., no changes in knowledge), we automatically
skip some rounds of phase 1. However, after a few skipped rounds, we periodically re-enable phase 1 to ensure that any new
knowledge or changes are still captured in the optimization process.
Additionally, if there are early exits, the cost can be further reduced. For example, in the object_counting task, the process
finished early at iteration 5, taking only about 1 minute, with 21,218 input tokens and 5,764 output tokens.

B.2. Reasoning Quality versus Token Efficiency
As reasoning-oriented models become stronger, the primary benefit of prompt optimization may shift from raw accuracy
improvements to inference efficiency. Especially for simpler tasks, smaller instruct models with optimized prompts may
achieve comparable performance to larger reasoning-heavy models while using significantly fewer tokens and thus incurring
lower inference costs. To study this effect, we compare Qwen3-8B with CoT prompting and Qwen2.5-7B-Instruct with an
MR.PEA-optimized prompt on BBH boolean_expressions.

  Table 8. Comparison between reasoning-heavy inference and MR.PEA-based prompt optimization on BBH boolean_expressions.

                          Metric                  Qwen3-8B + CoT       Qwen2.5-7B-Instruct + MR.PEA
                          Accuracy (%)                  97.60                        96.40
                          Avg. Output Tokens           721.65                        306.07
                          Output Token Range         [261, 1500]                   [130, 597]


Table 8 shows that although both configurations achieve comparable accuracy, the MR.PEA-optimized setup reduces output
token usage by more than 50%. Notably, the Qwen3-8B outputs were capped at 1500 tokens. Removing this limit would
likely further increase its average token consumption.
These results suggest that MR.PEA can enable smaller instruct models to achieve reasoning-level performance with
substantially lower inference cost and higher throughput. This property is particularly useful in practical deployments where
a single model may handle diverse sub-tasks where reasoning is only a fraction of the workload. Our framework empowers
these general-purpose instruct models to match specialized reasoning quality on-demand.

B.3. Comparison with Strong Teacher-Based Optimization
A natural question is whether prompt optimization using a substantially stronger frontier model would outperform a fully
self-supervised workflow operating on the target model itself. To investigate this, we compare three settings for optimizing
prompts for GPT-4.1-nano: (1) MR.PEA using GPT-4.1-nano alone as both the optimizer and target model (Student Only),
(2) MR.PEA augmented with web search (Student + Web), and (3) a teacher-student setup where GPT-5.3-chat optimizes
prompts for GPT-4.1-nano (Teacher-Student).
We evaluate these approaches on three BBH tasks where optimizing with the student model alone initially performs poorly.

              Table 9. Comparison between student-only and strong teacher-based prompt optimization on BBH tasks.

                        Task                      Student Only     Student + Web     Teacher-Student
                        movie_recommendation          59.60             64.40              62.40
                        ruin_names                    69.20             73.60              80.40
                        snarks                        67.42             74.16              78.09


Strong frontier models are highly effective prompt optimizers, particularly on tasks requiring broad world knowledge
or subtle semantic understanding. As shown in Table 9, the teacher-student setup achieves the best performance on two
of the three tasks, suggesting that stronger teacher models can effectively compensate for the knowledge limitations of
smaller student models during prompt optimization. At the same time, MR.PEA with web search substantially narrows
the performance gap, indicating that adaptive retrieval can partially compensate for the limited internal knowledge of the
student model. In practice, though using a frontier optimizer increases initial costs, it offers a robust and straightforward
path toward strong performance.

C. Experiment Settings
C.1. Big-Bench Hard Grouping
We divided the BIG-Bench Hard (BBH) tasks into five major categories to balance the number of tasks in each group and to
reflect the main types of reasoning or skills required. The categories are:
• Common Sense and Factual Judgment: Tasks that test common sense, factual knowledge, and the ability to detect errors
or lies, including causal_judgement, movie_recommendation, salient_translation_error_detection, sports_understanding,
web_of_lies.
• Language and Semantics: Tasks that require understanding language structure, semantics, and word manipulation,
including disambiguation_qa, hyperbaton, ruin_names, snarks, word_sorting.
• Logic and Reasoning: Tasks focused on logical deduction, formal reasoning, and evaluating logical expressions,
including boolean_expressions, formal_fallacies, logical_deduction_five_objects, logical_deduction_seven_objects, logi-
cal_deduction_three_objects.
• Mathematics and Arithmetic: Tasks involving mathematical calculations, counting, and geometric reasoning, including
date_understanding, dyck_languages, geometric_shapes, multistep_arithmetic_two, object_counting.
• Spatial, Sequential, and Attribute Reasoning: Tasks related to spatial relationships, sequences, and reasoning about
object attributes, including navigate, penguins_in_a_table, reasoning_about_colored_objects, temporal_sequences.

E.2. MR.PEA: Core Algorithm Pseudocode
We present the complete pseudo code of MR.PEA below.

Algorithm 2 Meta-Reasoning Prompt Engineering Agent (MR.PEA) Full Algorithm
Require: Task description τ , format requirements r, initial example x0
Ensure: Optimized prompt p∗
 1: Initialize:
 2: Initialize prompt p0 ← τ + r, best prompt p∗ ← p0 , knowledge k0 ← ∅, feedback f0 ← ∅
 3: Initialize prompt pool P ← {(p0 , βbase )} with base ranking scores
 4: M ← I NITIALIZE M EMORY(k0 , x0 , f0 , P)
 5: Set parameters: importance θimp , confidence θconf , bonus factor αbonus , decay factor γ
 6: Set counters: t ← 1, consecutive wins w ← 0, search count s ← 0
 7: Main Optimization Loop:
 8: while t ≤ Tmax and w < Twin do
 9: Phase 1: Task-Specific Knowledge Curation
10:    ktemp ← M ETA R EASON(τ, M.knowledge, M.example)
11:    if ktemp = M.knowledge or ktemp .needs_update = FALSE then
12:       kt ← M.knowledge                                                                         ▷ No knowledge update needed
13:    else
14:       if t ≥ 2 and s < Smax then
15:          decision ← M ETA D ECISION(τ, ktemp , t, s)
16:          I ← decision.importance, C ← decision.confidence                                                            ▷ Scores
17:          if decision.search_needed and I > θimp and C > θconf then
18:             q ← G ENERATE Q UERY(τ, decision.gap)
19:             kweb ← W EB S EARCH(q)
20:             ktemp ← I NTEGRATE K NOWLEDGE(ktemp , kweb ), s ← s + 1
21:          end if
22:       end if
23:       kt ← ktemp , M.knowledge ← M.knowledge ∪ {kt }
24:    end if
25:
26:    Phase 2: Diverse Validation Example Generation
27:    X ← G ET R ECENT E XAMPLES(M.examples, n)                                                       ▷ Include n latest examples
28:    xt ← G ENERATE E XAMPLE(τ, kt , X )
29:    M.examples ← M.examples ∪ {xt }
30:
31:    Phase 3: Strategy-Guided Prompt Refinement
32:    H ← G ET T OP P ROMPTS(P, m)                                                             ▷ Include m historical top prompts
33:    pt ← R EFINE P ROMPT(τ, kt , xt , M.feedback, H)
34:
35:    Phase 4: Criteria-Based Pairwise Evaluation
36:    y ∗ ← ϕ(p∗ , xt ), yt ← ϕ(pt , xt )                                                                     ▷ Execute prompts
37:    (pwin , ft ) ← PAIRWISE E VALUATE((p∗ , y ∗ ), (pt , yt ), kt , xt )
38:    M.feedback ← M.feedback ∪ {ft }
39:
40:    Phase 5: Dynamic Prompt Pool Management
41:    if pwin = pt then
42:       score(pt ) ← βbase + t · αbonus
43:       p∗ ← pt , w ← 0
44: else
45:       ∀p ∈ P : score(p) ← γ · score(p)
46:       score(p∗ ) ← score(p∗ ) + t · αbonus
47:       score(pt ) ← βbase , w ← w + 1
48: end if
49: P ← P ∪ {(pt , score(pt ))}, t ← t + 1                                                                  ▷ Add to prompt pool
50: end while
51: return arg maxp∈P score(p)
