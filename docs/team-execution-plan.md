# 团队执行计划

## 总体依赖

阶段一完成共同起点后，后续分成两条并行工作流：

```text
阶段一：Meta-Harness × Terminal-Bench 2.0 + 每个负责方向 2 篇论文
   ├─ 工作流 A：复现全部 Baseline × Benchmark ───────────────┐
   └─ 工作流 B：扩充并核验知识库 → 分配 Method → 建独立仓库 → 实现 ─┤
                                                              └─ 汇合验证
```

工作流 A 与工作流 B 并行；工作流 B 内部严格按照“知识库扩充 → Method 分配与建库 → Method 实现”的顺序执行。

## 阶段一：完成已分配的共同任务

| 清单 | 执行要求 | 完成条件 |
| --- | --- | --- |
| 复现 `Meta-Harness × Terminal-Bench 2.0` | 五位成员分别在 `reproductions/<成员>/meta-harness/terminal-bench-2.0/` 保存源码、环境、配置、trace、分数、成本、失败记录和复现说明。 | 五个独立目录都能按说明启动；实验协议与结果字段一致；失败也有可审计记录。 |
| 收集负责方向的论文 | 按 [knowledge/README.md](../knowledge/README.md) 的既有分工，每个方向整理 2 个合格 `SourcePacket`，放入 `knowledge/source-packets/<source-id>/`，并更新知识索引。 | 每个方向达到 `2 / 2`；论文、官方代码、来源锚点、配置、测试和报告结果齐全，缺失项明确标为未知。 |
| 对齐共同协议 | 固定执行模型、优化模型、H0、数据角色、评测器、seed、环境版本、成本口径和日志 schema；个人配置保存在各自复现目录。 | 五份复现结果可以逐字段比较，未混用 train/select/anchor/test。 |

## 阶段二 A：复现全部 Baseline × Benchmark

本工作流在阶段一协议稳定后启动，可以贯穿阶段二 B 及其后的阶段三，与“知识库扩充 → Method 建库与实现”整条串行链并行推进。

| 清单 | 范围 | 执行位置与要求 |
| --- | --- | --- |
| 固定三个 benchmark 的 H0 | Terminal-Bench 2.0、GAIA2、SWE-Bench Pro | 在 `reproductions/<成员>/H0/<benchmark>/` 运行 benchmark 官方 H0，记录版本、数据划分、模型、配置、结果和成本。 |
| 复现三个优化 baseline | GEPA、Meta-Harness、AutoSaddler | 覆盖三个 benchmark；结果放入 `reproductions/<成员>/<baseline>/<benchmark>/`。优先复现论文原设置，再补统一 H0 对照。 |
| 完成实验矩阵 | 4 个 baseline × 3 个 benchmark | 每个组合至少有一份完整复现；关键结果由另一成员交叉核验。任务负责人和算力安排另行登记，避免五人重复跑完整矩阵。 |
| 汇总可比结果 | 分数、成功率、token、费用、时延、失败类型与环境差异 | 使用统一结果 schema；不同 H0、模型、评测器或数据划分不得直接合并。 |

## 阶段二 B：扩充并核验知识库

| 清单 | 执行要求 | 完成条件 |
| --- | --- | --- |
| 完成基础覆盖 | 补齐 `knowledge/README.md` 中全部方向，每个方向至少 2 个合格来源包。 | 所有方向达到基础覆盖，重复论文不重复计数。 |
| 补齐 Method 所需机制 | 根据五份 [Method 详解](methods/detailed/README.md) 检查组织检索、候选生成、演化控制和长期复用所需机制。 | 每个关键机制至少有可追溯论文或工程来源；没有成熟来源时明确登记知识缺口。 |
| 执行质量复核 | 核对论文版本、官方代码、原文锚点、实现接口、实验条件、收益、成本和失败边界。 | SourcePacket 通过结构检查和人工复核；未经核验内容不进入可调用知识层。 |
| 建立关系与索引 | 标注依赖、替代、组合、冲突、适用条件及代码入口。 | 五条 Method 能按自身状态表示检索并定位到可接入材料。 |

## 阶段三：分配 Method 并建立独立仓库

本阶段必须在阶段二 B 达到知识库完成条件后启动。五份 Method 暂不分工。

| Method | 负责人 | 独立 GitHub 仓库 | 建库前置条件 |
| --- | --- | --- | --- |
| 证据约束的反例演化 | 待分配 | 待创建 | Method 详解、共用接口和相关知识来源冻结。 |
| 程序结构库与渐增拓扑协同演化 | 待分配 | 待创建 | Method 详解、共用接口和相关知识来源冻结。 |
| 条件化案例与优化器组合 | 待分配 | 待创建 | Method 详解、共用接口和相关知识来源冻结。 |
| 实验驱动的干预版本空间演化 | 待分配 | 待创建 | Method 详解、共用接口和相关知识来源冻结。 |
| 决策论驱动的信念演化 | 待分配 | 待创建 | Method 详解、共用接口和相关知识来源冻结。 |

建库时统一放入：对应 Method 详解、知识库读取接口、候选 Harness 接口、trace/账本 schema、实验配置模板、最小测试和复现说明。每个仓库独立开发，不在本仓库混放实现代码。

## 阶段四：实现五条 Method

| 清单 | 执行要求 | 完成条件 |
| --- | --- | --- |
| 跑通单轮链路 | 外部方法检索 → trace 诊断 → 候选生成 → 核验 → 一次测评 → 状态写回。 | 每一步有真实输入、输出、调用记录和失败语义。 |
| 跑通多轮演化 | 支持 `H0 → H1 → H2 → ...`，包括返回检索、返回候选生成、回滚和停止。 | 训练 loop 可恢复、可重放，测试集始终隔离。 |
| 完成消融 | 分别移除外部知识、trace、自由探索和长期复用。 | 能区分各模块贡献，并记录性能与成本变化。 |
| 接入共同实验协议 | 使用阶段二 A 的 H0、benchmark、模型、评测器和结果 schema。 | Method 结果可以和全部 baseline 公平比较。 |

## 阶段五：汇合验证

| 清单 | 执行要求 | 完成条件 |
| --- | --- | --- |
| 主结果对比 | 五条 Method 与 H0、GEPA、Meta-Harness、AutoSaddler 在三个 benchmark 上比较。 | 报告相同协议下的效果、成本、方差和失败类型。 |
| 泛化与能力保留 | 检查未见任务、跨 benchmark 迁移、anchor 能力和严重失败。 | 新能力提升不以不可接受的旧能力退化为代价。 |
| 统一复核 | 复核代码版本、数据角色、配置、日志、结果和结论。 | 所有主张可回到仓库 revision、SourcePacket 或真实运行证据。 |
