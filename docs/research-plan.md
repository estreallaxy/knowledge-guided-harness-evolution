# 研究方案：以持续积累的方法知识增强任务导向的 harness 构建与优化

本方案研究优化 agent 的能力增强，涵盖方法知识积累、任务导向构建、自主探索与反馈优化。下文保留核心动机，并列出各阶段需要讨论的问题。

## 1. 研究动机与核心 idea

### 1.1 Motivation

1. Harness 的自动构建与演化依赖优化 agent 理解任务、分析执行轨迹、提出改进机制并将其正确实现，但通用编码能力并不必然转化为高效的 harness 优化能力。Trace 能揭示已发生的行为和失败，却不能完整提供可能的解决方案；
2. 模型已有的相关策略也可能未被当前上下文有效调用，使优化停留在有限的修改模式中。与此同时，外部论文与工程实践提供了可供借鉴的方法，但这些知识分散在不同描述和实现中，需要经过提炼、核验与适配，才能成为优化 agent 可使用的策略。
3. 实际任务对 skill、工具、上下文、记忆和容错的需求各不相同，成熟框架及单个方法的效果也不能直接等同于其迁移、组合后的收益，因此需要将任务需求与方法的适用条件、接口依赖和成本联系起来，支持从初始构建到后续优化的完整过程。

由此，本研究关注如何增强优化 agent 本身构建和改进 harness 的能力：持续吸收经过复核的外部方法知识，结合渐进式披露与自身实验经验，使其更有效地选择、适配和组合已有机制，同时保留独立提出、修改或拒绝方案的自由，避免知识引导固化探索。最终目标是在有限预算下提高有效改进的产生与实现效率，并通过执行反馈持续纠正方法选择和组合，检验多轮优化中的旧能力保留与未见任务收益。

### 1.2 核心 idea 与方法主线

**一句话 idea：通过持续吸收并核验外部方法知识、引导优化 agent 的自主探索和积累实验经验，增强其面向任务的 harness 构建与优化能力；先根据任务需求选择、适配和组合方法，再结合执行轨迹持续改进，并验证成本、能力保留与泛化效果。**

外部知识主要给优化 agent；执行 agent 使用优化后得到的代码、配置、工具和技能，不需要默认携带整套研究知识库。

两个阶段相互连接：

1. **任务导向的初始构建**：任务需求 + 可编辑系统 + 方法知识 + 自主提案 → 候选初始 harness。
2. **证据驱动的持续优化**：当前 harness + trace + 历史实验 + 方法知识 + 自主提案 → 候选修改 → 验证 → 保留、修订或撤销。

两个知识来源相互补充：

- **外部研究知识**：论文和工程实践提供可能的机制、实现方式及适用条件。
- **内部探索经验**：优化 agent 自主提出假设，并从真实成功、失败和对照中积累经验。

核心研究问题是：**在固定执行模型、优化模型和资源约束下，能否让优化 agent 更善于提出和实现有效改进，并通过持续吸收外部知识与自主探索，改善任务适配、优化效率和跨任务收益，同时控制旧能力退化？**

## 2. Method：从方法知识到 harness 优化

以下是拟采用的工作流程。各阶段先明确产物与操作，算法、选择权重和晋升门槛再通过实验确定。

| 阶段 | 要完成的事 | 产物 |
| --- | --- | --- |
| 2.1 收集与整理 | 筛选论文和工程实践，核验并维护可迁移的方法知识。 | 可检索、可追溯的方法卡及其使用边界。 |
| 2.2 初始化 | 对照任务需求与原版 harness，选择、适配和组合方法。 | 初始 harness 及选择记录。 |
| 2.3 优化 | 从执行 trace 诊断问题，自主或借助知识提出修改、验证并积累经验。 | 下一版本 harness 与可复用的成败记录。 |

统一评测、baseline、benchmark、消融和成本核算见第 3 章。

| 核心评价指标             | 如何使用该指标进行评价                                       |
| ------------------------ | ------------------------------------------------------------ |
| **问题相关性**           | 是否解决目标任务或 harness 的具体瓶颈？与已发现的失败类型、优化需求直接相关的，优先收集。 |

| **知识增量与互补性**     | 相比已有材料，是否带来新机制、新适用条件或不同的成本收益取舍？优先补充缺失能力，降低重复方法的收集优先级。 |

每个可迁移机制对应一个供优化 agent 渐进读取的方法目录：

| 要做什么 | 每个方法目录需要回答的问题或保留的内容 |
| --- | --- |
| 提取机制 | 要解决什么瓶颈、作用于哪个 harness 模块？输入、触发条件、必要步骤、状态变化和预期输出是什么？ |
| 标注使用边界 | 依赖哪些任务、模型、工具、环境和预算条件？已知在哪些条件下失效，哪些条件尚未验证？ |
| 绑定实现与效果 | 固定论文、代码和配置版本；链接原文位置、关键接口、示例、实验对照、收益、成本与副作用。区分论文主张、代码实际行为和拟迁移的设想。 |
| 建立方法关系 | 标出依赖、替代、组合、冲突或变体；注明哪些关系已有证据，哪些只是待测假设。整体系统收益不直接归因于单个机制。 |
| 核验并入库 | 提取 agent 生成草稿；自动检查链接、版本和数值，条件允许时运行最小示例；人工复核高价值或存疑条目的机制、遗漏条件与错误归因。缺失信息写“未知”。 |

默认读取路径只有三层：`knowledge/README.md` 用于快速筛选；`methods/<method>/README.md` 说明采用条件、干预过程、边界和运行入口；确定采用后直接调用 `code/` 中随仓库保存的代码、配置与提示模板，不再临时检索论文或代码仓库。`evidence/` 和 `sources/` 独立保存论文结果、固定版本映射与核验记录，仅在审计来源或研究结论时读取。该组织借鉴优秀 Skill 的低成本发现、按需展开和自包含实现思路，但不照搬其文件命名或固定模板。**此阶段只核实知识描述，不把原论文的有效性当作目标 harness 的迁移效果。**

知识库还要吸收本地实验经验，但保留两类证据的区别：**外部材料证明原方法是什么，本地实验检验迁移后是否有效**。原始论文、代码版本、运行记录和 harness 差异保留不改；方法页的归纳、适用范围和推荐状态可随新证据修订。

| 知识维护 | 要做什么 |
| --- | --- |
| 关联外部与内部证据 | 将方法连接到采用、改造、组合或拒绝它的 harness 修改及实验记录；自主提出的机制也可进入候选列表。人工优先复核高影响、冲突或存疑条目。 |
| 更新适用范围 | 区分“机制描述已核实”“在当前任务局部有效”“在未见同类任务有效”“跨环境有效”；只在已验证条件下推荐，未验证条件保持开放。 |
| 处理重复与冲突 | 按机制和条件关联近似方法，保留各自来源；并列记录冲突结论及任务、模型、harness、预算、评测器和版本条件，同条件冲突再做对照。 |
| 处理过时与误导 | 上游代码、接口、模型或 benchmark 改变，或后续实验发现退化时，标记相关条目待复查并暂停主动推荐；不因一次成败自动晋升或淘汰。 |

后续任务按能力缺口、方法前提和相似实验检索，并记录优化 agent 查看、采用、改造或拒绝条目后的结果。知识条目的推荐范围由迁移证据决定，不能由当前 harness 上一次修改是否被保留直接推断。条目积累和过早淘汰的风险可参考 [Library Drift](https://arxiv.org/html/2605.19576)；外部方法知识库的实际收益仍需第 3 章检验。

### 2.2 如何初始化：根据任务选择、适配与组合方法

**本节产物：**在目标任务尚无执行 trace 时，从固定的原版 `H0` 形成可运行的初始 harness `H1`，并留下任务需求、方法选择和修改理由。运行后的失败分析放在 2.3。

| 步骤 | 要做什么 | 输出 |
| --- | --- | --- |
| 1. 找能力缺口 | 描述任务实例与任务族的目标、验收标准、工具、状态跨度、权限和预算；记录 `H0` 已有能力及可编辑接口。 | “任务需要什么、`H0` 缺什么”的清单。 |
| 2. 筛方法 | 按缺口检索方法卡；先检查工具、接口、模型和预算等硬条件，再比较适配程度、原始证据、预期收益、接入成本与退化风险。语义相似度只用于发现候选。 | 少量可尝试的方法及不采用的理由。 |
| 3. 定迁移与组合 | 检查输入输出、共享状态、触发时机、执行顺序、依赖、重复和冲突；允许修改库内方法或提出库外方案。 | 单方法或组合的修改方案，以及预期机制。 |
| 4. 实现并筛选 | 在相同底座和执行模型上实现候选，先检查可运行性，再用开发任务比较效果、token、时延和原有能力退化；必要时保留 `H0`。 | 初始版本 `H1`、代码差异和选择记录。 |

组合收益需要实测：对候选 A、B，在**相同底座、模型和开发任务**上比较 `H0`、`H0+A`、`H0+B`、`H0+A+B`。目标测试任务的 trace 不参与初始化；原论文收益仅作先验，方法权重和组合收益待开发集实验校准。相关依据见 [Task-Aware Harness Provisioning](https://arxiv.org/abs/2608.17433)、[SkVM](https://arxiv.org/abs/2604.03088) 和 [SkillWeaver](https://arxiv.org/abs/2606.18051)。

### 2.3 如何优化：结合 trace、知识与自主探索

**本节产物：**每轮形成有证据的修改假设、可运行的候选 harness、验证结果和下一版本，并把成功、失败及未采用候选记录下来，反馈到 2.1 的知识库。优化 agent 自主决定查看哪些证据、是否检索知识及尝试什么修改。

| 步骤 | 优化 agent 要做什么 | 关键检查 |
| --- | --- | --- |
| 1. 看执行证据 | 先看结果和 trace 摘要，按需展开原始步骤；对照同类任务的成功、失败行为及工具、环境状态。证据不足时可重跑或增加针对性观测。 | 问题是否确实来自可修改的 harness？哪些成功行为需要保留？ |
| 2. 提出假设 | 从反复出现的现象定位模块与失败机制，说明预期改变的行为及不确定性。 | 区分 harness 缺陷、执行模型能力不足与任务环境问题。 |
| 3. 寻找并实现改法 | 自主构思，或按失败机制、作用模块和适用条件检索方法卡及历史实验；可借鉴、改造、组合或拒绝已有方法。将方案落实为尽量可归因的代码、配置或指令修改。 | 修改是否满足前提？触发条件、潜在冲突和验证信号是什么？ |
| 4. 验证并选择 | 先检查候选能否运行、预期机制是否触发，再在开发任务及既有成功任务上比较效果、成本与退化；保留、修订或撤销修改。 | 改善是否超出偶然波动？若反复无效，是否应换模块或探索路径？ |

Trace 的采集与展示本身也是可修改的 harness 部分：优化 agent 可决定记录什么、何时请求或展开证据，同时考虑额外 token 与时延。**原始运行记录和外部评测结果独立保存**，用于核对前后行为；不预设固定候选路径数或通用评分权重。可借鉴 [HarnessFix](https://arxiv.org/abs/2606.06324) 的轨迹到实现定位、[ModularRSI](https://arxiv.org/abs/2609.14857) 的成败轨迹对照、[HarnessCompass](https://arxiv.org/abs/2608.01918) 的反馈核对、[HarnessBank](https://arxiv.org/abs/2607.13683) 的多路径保留和 [RRSI](https://arxiv.org/abs/2609.24972) 的修改历史记录。

每轮保存任务与环境版本、修改假设、借鉴或自主提出的方法、代码差异、机制触发证据、效果、成本及保留或撤销原因。一次修改能否进入下一版 harness，由**当前开发任务的验证结果及既有能力检查**决定；经验能否推荐给未来任务，另按 2.1 的迁移证据判断。开发任务用于选择候选，封存的测试任务不参与优化；知识库检索也不能提前暴露测试题答案。反复优化时重测既有成功任务，并在收益接近运行波动时继续收集证据，不凭单次得分定论。相关验证与经验积累可参考 [AutoSaddler](https://arxiv.org/html/2608.23041) 和 [RRSI](https://arxiv.org/html/2609.24972)。



## 3. Experiment：效果、泛化、能力保留与成本

**本节产物：**固定的实验协议、同条件下重跑的 baseline 结果，以及完整方法和各组成部分的效果、泛化与成本报告。先在 Terminal-Bench 2.0 建立 `H0`、Meta-Harness、AutoSaddler 的主对照，再用 GAIA2 检查跨环境收益；其他方法按要检验的问题和复现成本加入。

### 3.1 实验协议与评价问题

| 要做什么 | 具体要求 |
| --- | --- |
| 1. 固定共同协议 | 固定执行模型、优化模型、`H0`、可编辑范围、任务清单、训练/开发/测试划分、判分器、环境和候选/rollout 预算；所有方法从同一底座重跑。论文原有分数只作参考。 |
| 2. 跑方法对照 | 比较 `H0`、核心 baseline 和完整方法；补充方法用于回答特定问题，而非只增加对照数量。 |
| 3. 拆解贡献 | 分别去掉任务导向初始化、外部方法知识、trace 驱动优化；比较只复用库内方法与允许自主提出库外方案，并区分结构化方法卡和直接提供原始文献的效果。 |
| 4. 查泛化与退化 | 用开发集选候选、封存测试集；按任务族、仓库或环境划分未见任务，每轮重测既有成功任务，报告新增成功和原有成功退化。 |
| 5. 算完整成本 | 记录收集、整理和人工复核工时，baseline 适配工时，优化器与执行器 token/费用、运行时间和推理时额外开销；报告单位预算增益。 |

### 3.2 方法 baseline

| 方法 baseline | 定位与纳入理由 |
| --- | --- |
| 未优化的 `H0` | 所有方法共同起点，用于衡量真实增益和旧能力变化。 |
| [Meta-Harness](https://arxiv.org/abs/2603.28052)（[代码](https://github.com/stanford-iris-lab/meta-harness)） | **核心对照**：自主读取代码、分数和 trace 并修改 harness；[项目页](https://yoonholee.com/meta-harness/)标注 COLM 2026。用于检验知识引导相对自主代码搜索的收益。 |
| [AutoSaddler](https://arxiv.org/abs/2608.23041)（[代码](https://github.com/microsoft/AutoSaddler)） | **核心强对照与协议参考**：列入 [NeurIPS 2026 官方论文名单](https://neurips.cc/Downloads/2026)，在三个 benchmark 上重跑 Meta-Harness。论文实验使用 V1；公开的 [V1 操作说明](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v1/README.md)主要覆盖 Meta-ARE/GAIA2，其他环境的适配须单独核查。 |
| [ModularRSI](https://arxiv.org/abs/2609.14857)（[代码](https://github.com/IQuestLab/ModularRSI)） | 补充分模块优化对照；预印本，在统一 Terminal-Bench 2.0 设置下重跑 Meta-Harness 和 AHE。 |
| [HarnessFix](https://arxiv.org/abs/2606.06324)（[代码](https://github.com/HarnessFix/HarnessFix)） | 补充 trace 诊断与修复对照；预印本，在 GAIA、SWE、AppWorld 和 Terminal-Bench 2.0 上比较 Meta-Harness。 |
| [RHO](https://arxiv.org/abs/2606.05922)（[代码](https://github.com/wbopan/retro-harness)） | 补充无验证标签场景；论文注明 EMNLP 2026 Findings，在 SWE-Bench Pro 上直接比较 Meta-Harness；反馈条件不同，需单独报告。 |

其他已实际重跑 Meta-Harness 的工作包括 [RRSI](https://arxiv.org/abs/2609.24972)（Terminal-Bench 2.1 与跨域泛化）、[HarnessLens](https://arxiv.org/abs/2608.27311)（多执行 harness）和 [Adaptive Auto-Harness](https://arxiv.org/abs/2606.01770)（长期任务流）。[VeRO](https://arxiv.org/abs/2602.22480) 与 [HarnessOpt-Bench](https://arxiv.org/abs/2608.06301) 是可考虑的独立评测平台，不作为方法 baseline。

### 3.3 Benchmark 与划分

| Benchmark | 在本研究中怎么用 | 协议边界 |
| --- | --- | --- |
| [Terminal-Bench 2.0](https://arxiv.org/abs/2601.11868) | **主实验**；Meta-Harness、AutoSaddler、ModularRSI、HarnessFix 共同使用，论文列入 [ICLR 2026](https://iclr.cc/virtual/2026/papers.html)。 | 可参考 AutoSaddler 的 **30/19/40** 训练/开发/测试划分，但须取得并固定任务清单。Meta-Harness 原文在同一套任务上搜索并报告结果，其分数不能直接与留出测试集比较。 |
| [GAIA2](https://arxiv.org/abs/2602.11964) | **第二环境**；列入 ICLR 2026，借鉴 AutoSaddler 的跨 Universe 划分检查泛化。 | 核对 Meta-ARE 版本、场景清单、判分器和模型。 |
| [SWE-Bench Pro](https://arxiv.org/abs/2509.16941) | **仓库级补充实验**；AutoSaddler 与 RHO 已用于比较 Meta-Harness。 | 适配成本较高；固定公开集、仓库划分和版本，关注 [Verified 修订](https://arxiv.org/abs/2609.08149)。 |
| [Terminal-Bench 2.1](https://www.tbench.ai/news/terminal-bench-2-1) | **版本稳健性复查**；RRSI 使用该版本。 | 官方修正了 2.0 中 89 题里的 28 题；各方法须重跑，不与 2.0 分数混算。 |

外部知识要保存来源和收集时间，并排除测试题答案及 benchmark 专属修补；结果注明是直接复现还是重新适配。对照与划分依据主要见 [AutoSaddler](https://arxiv.org/html/2608.23041)、[ModularRSI](https://arxiv.org/html/2609.14857) 和 [RHO](https://arxiv.org/html/2606.05922)。



## 4. 规划：先建立可比起点，再实现与检验方法

第一组实验采用 **Meta-Harness + Terminal-Bench 2.0**：前者对应自主代码搜索，后者使用仓库中已经固定的数据快照与训练/开发/测试划分。当前工作从运行共同 H0 和复现 Meta-Harness 开始。**Baseline 是优化方法，`H0` 是各方法共同使用的初始执行 harness，两者不能混为一谈。**

三位同学的并行分工、阶段依赖和汇合条件见[三阶段并行执行计划](team-execution-plan.md)。

### 4.1 第一阶段：运行共同 H0 并复现 Meta-Harness

| 工作 | 本阶段要完成什么 | 产物与完成条件 |
| --- | --- | --- |
| 运行共同 `H0` | 周梦凡使用统一配置运行 Terminus-KIRA：先完成一个 train 任务 smoke test，再运行冻结的训练集。 | 可重复的运行命令、原始 trace、逐题分数、token、费用与时延。 |
| 复现 Meta-Harness | 赵星源使用统一配置跑通官方 KIRA 流程，再迁移到共同数据划分与预算；同时保留 Terminus 2 初始 baseline。 | 可重复执行的 baseline 流程、候选代码与日志；结果标记为论文设置复现或共同协议适配。 |
| 统一实验配置 | 王懿统一维护公共配置、H0 入口配置和 Meta-Harness 入口配置；另外两人只消费配置。 | 三份配置位于 `experiments/configs/`；公共参数变化后两条实验线一起重跑。 |
| 收集并整理方法 | 三人按 2.1 的负责人并行收集各方向论文与工程方法；每个方向先完成一项，再继续扩展。 | 链接回填 2.1；原始材料进入 `knowledge/sources/`，方法说明与可用代码进入 `knowledge/methods/`。 |

**进入第二阶段的条件：**共同 `H0` 和 Meta-Harness 能在同一开发任务、模型与预算下稳定运行；2.1 每个方向至少登记一项材料，并形成对应的方法目录。

### 4.2 第二阶段：实现最小的知识引导优化闭环

| 工作 | 待解决的实现问题 | 目标与检查点 |
| --- | --- | --- |
| 任务导向初始化 `H0 → H1` | 如何描述任务缺口与 `H0` 能力，何时检索方法卡，怎样判断适用性、实现候选及保留自主提出的方案？先用首张卡打通流程，再逐步扩展方向。 | 产出可运行的 `H1`、选择理由和代码差异；在开发任务上核对方法是否真正触发、是否改善行为及是否损伤 `H0` 已有能力。算法与权重留待实验决定。 |
| Trace 驱动的迭代 `Ht → Ht+1` | 如何让优化 agent 从成败轨迹提出可检验假设，选择查知识、改造已有方法或自由探索，并在修改后检查机制、效果和退化？trace 的采集与展示也允许作为任务侧 harness 的修改对象。 | 至少完成一次“运行—诊断—修改—开发集验证—保留或撤销”的闭环；保存原始 trace、知识使用记录、候选版本和失败尝试。 |
| 经验回写 | 如何把外部方法、实际修改和实验结果关联起来，区分“原文机制成立”“本任务有效”和“可推荐给新任务”？ | 将成功与失败记录反馈到 2.1 的方法卡，保留来源和适用条件；不因单次结果自动推广或淘汰。 |

第二阶段先证明流程**能够工作、能够追溯且能做公平对照**。`H1` 或迭代版本是否优于强 baseline，由下一阶段的封存测试和消融判断，不能用开发集上的最佳一次结果代替。

### 4.3 第三阶段：扩大知识覆盖并验证贡献

| 工作 | 要回答的问题 | 主要结果 |
| --- | --- | --- |
| 扩充方法卡 | 不同 harness 模块和方法组合是否带来比单张卡更有意义的搜索空间？哪些条目重复、冲突或不适用？ | 带来源与复核状态的多方向方法库，以及实际被采用、改造或拒绝的记录。 |
| 同条件对照与消融 | 在相同 `H0`、模型、数据划分和预算下，完整方法相对 Meta-Harness 等 baseline 有何增益？增益来自初始化、结构化知识还是自主探索？直接提供原始论文能否达到相同效果？ | 第 3 章规定的完整对照、关键消融及重复运行结果。 |
| 泛化、保留与总成本 | 开发集上的改进能否转移到封存测试任务和第二环境？旧能力是否退化？收集、复核、代码适配及运行成本是否值得？ | 未见任务表现、新增成功与原有成功退化、有效修改所需尝试次数，以及完整人力和计算成本。 |
